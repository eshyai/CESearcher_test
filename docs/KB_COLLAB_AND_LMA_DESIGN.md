## 总览：两件事其实是同一条链

```text
        人的知识（沉淀）                          机器的偏好（进化）
   ┌────────────────────────┐            ┌────────────────────────┐
   │  共享知识库             │            │  LMA 偏好画像          │
   │  文档 · 切片 · 标注     │            │  关注主题 · 权重 · 置信 │
   └───────────┬────────────┘            └───────────┬────────────┘
               │                                      │
               └────────────► 统一信号 ───────────────┘
                    （标签 / 重要度 / 反馈 / 检索行为）
                                  │
                                  ▼
                          排序 & 检索 & 回答
```

两者共用一套「**信号**」概念：知识库的标注是**人对内容的判断**，LMA 是**机器对偏好的判断**。分开建设、共用一条信号总线，是这份设计的主线。

# 第一部分 · 知识库：从「私有文档柜」到「多人协作空间」

## 1.1 现状盘点（已核实代码）

| 能力 | 后端 | 前端 | 结论 |
|---|---|---|---|
| 知识库 CRUD | ✅ `knowledge_router.py` | ✅ `pages/knowledge` | 可用 |
| 文档上传 + 切片 | ✅ Milvus `kb_{名称}` 集合 | ✅ 上传弹窗 | 可用 |
| 软删除 + 恢复 | ✅ `deleted_at` + `/restore` | ✅ 文档级有恢复 | 基本可用 |
| 修订号 | ✅ `revision` 字段（kb / doc 都有） | ❌ 未展示 | 半成品 |
| **成员角色** viewer/editor/manager | ✅ 模型 + 4 个接口全在 | ❌ **零 UI** | **后端空转** |
| **审计日志** | ✅ 模型 + `/audit` 接口 | ❌ **零 UI** | **后端空转** |
| **标注**（评论/高亮/标签/评分） | ❌ 完全不存在 | ❌ 完全不存在 | **从零建** |
| 检索隔离 | ⚠️ scout 枚举所有 `kb_*` 集合，**不区分归属与权限** | — | **有越权风险** |

**一句话结论**：协作的"骨架"后端已经建好了（成员表、审计表、角色校验都在跑），只是**前端没有入口，所以整套能力等于不存在**；而"标注"是真正的新东西。

### 三个必须顺带修掉的既有问题

1. ✅ **`is_shared` 是隐形开关**（**已在 K1 修复**，见附录 B.1）。原实现 `role = member.role if member and kb.is_shared else None` —— 不把 `is_shared` 置 True，加再多成员也无法访问。现在成员身份即生效，`is_shared` 不再作为门槛。
2. ✅ **`list_members` 要求 manager 权限**（**已在 K1 修复**）。已放宽到 viewer 可读，并在名单中带出创建者。
3. ✅ **检索不按知识库隔离**（**已在 K2 修复**，见附录 C）。原实现枚举所有 `kb_*` 集合，A 的私有知识库会出现在 B 的回答里。现已改为只检索当前用户可见库的集合，并把集合命名从 `kb_{名称}` 换成 `kb_{uuid hex}`——后者还顺带修掉了**不同用户同名库写进同一集合**的物理串数据问题。

## 1.2 目标形态

一层容器、三层内容、一层人：

```text
知识库 (KnowledgeBase)
 ├── 权限层   owner / manager / editor / viewer        ← 已有
 ├── 内容层   文档 (Document) → 切片 (Chunk/向量)        ← 已有
 └── 人的层   标注 (Annotation)                          ← 新建
                ├─ 评论批注：就某段话讨论，可 @ 成员、可回复
                ├─ 划线高亮：锚定切片内的字符区间
                ├─ 标签分类：工艺/产品/政策/竞品…（受控词表）
                └─ 重要度评分：人工判定权威性，反哺检索加权
```

角色语义（沿用现有 `ROLE_RANK = viewer 1 / editor 2 / manager 3`）：

| 角色 | 看库 | 传/删文档 | 管成员 | 标注 | 看审计 |
|---|---|---|---|---|---|
| viewer | ✅ | ❌ | ❌ | ✅ 发表评论/高亮 | ❌ |
| editor | ✅ | ✅ | ❌ | ✅ | ❌ |
| manager | ✅ | ✅ | ✅ | ✅（可删任意标注） | ✅ |
| owner(创建者) | ✅ | ✅ | ✅ | ✅ | ✅ |

另建议补一档**可见性** `visibility: private | team`（详见第五部分决策 4）：
`team` 表示部门内所有登录用户可见，角色默认 viewer，可被提权。
有了它，「部门共享空间」才不用靠管理员逐个手工加人。

## 1.3 标注（Annotation）数据模型设计

**统一一张表**，用 `kind` 区分四种形态，避免四张表各自演化后无法统一检索：

```text
annotations
  id                UUID
  knowledge_base_id UUID   (FK, CASCADE)
  target_type       enum   chunk | document | knowledge_base
  target_id         UUID   被标注对象
  kind              enum   comment | highlight | tag | rating
  author_id         UUID   (FK users, SET NULL 保留痕迹)
  content           text    评论正文 / 标签名 / 评分值
  anchor            jsonb   定位信息（见下）
  visibility        enum   private | shared     默认 shared
  parent_id         UUID   评论回复用（自引用）
  status            enum   open | resolved | deleted
  revision          int     乐观锁
  created_at / updated_at
```

`anchor` 的三种形态：

| kind | anchor 内容 | 说明 |
|---|---|---|
| comment | `{"chunk_index": 3}` 或空 | 空 = 针对整篇文档 |
| highlight | `{"chunk_index": 3, "start": 12, "end": 40, "quote": "…"}` | 存 `quote` 原文用于切片重切后的模糊重定位 |
| tag | `{"tag": "工艺", "taxonomy": "business"}` | 建议受控词表，避免"工艺/技术/technique"三个标签并存 |
| rating | `{"score": 4, "scale": 5, "dimension": "authority"}` | 建议固定维度：权威性/时效性/相关性 |

**四个设计要点**：

- **切片会重切**。文档重传会生成新的 chunk 索引，锚点必须靠 `quote` 模糊重定位，不能只存下标。
- **标注要能软删除**。与知识库/文档保持一致，`status=deleted` 而非物理删除，审计可追溯。
- **私有/共享粒度**。允许个人给自己打"待读/存疑"标记，不污染团队视图。
- **审计接入**。标注的增删改统一写 `KnowledgeAuditLog`（`target_type='annotation'`），复用现有表，不新增。

## 1.4 标注不该只是"展示"，要回流到检索

这是标注真正的价值点，也是它和"加个评论区"的区别：

1. **标签 → 检索过滤/加权**。搜"己内酰胺"时可只搜带 `产品` 标签的切片；团队公认的 `政策` 标签文档优先。
2. **重要度 → rerank 加权**。现有链路是 `向量 ∪ 关键词 → rerank → MIN_SCORE=0.05`，把人工重要度作为 rerank 之后的一个乘子（如 `× (0.8 + 0.4 × 归一化重要度)`），让"人确认过的内容"稳定上浮。
3. **高亮/评论 → 回答引用**。DeepResearch 生成结论时，把相关切片上的团队批注一并带出，形成"这段结论来自谁在什么时候的判断"，比纯引用原文可信得多。
4. **评论 → LMA 信号**。反复被评论、被 resolve 的话题，本身是"团队关心什么"的证据，可作为第二部分偏好学习的输入。

# 第二部分 · LMA：让系统自己学会「该关注什么」

> **术语说明**：LMA 是你提出的说法，我先按「**L**earning **M**emory **A**gent —— 由大模型驱动、可解释、可回滚的偏好自主演进机制」来展开。如果你的原意更接近别的（比如模型微调/对齐），告诉我，我再调整方向。

## 2.1 现状：规则版偏好学习（已核实）

```
用户点「感兴趣/不感兴趣/相关/不相关」
        │
        ▼
feedback_signal()   →  平均成一个 -1 ~ +1 的信号
        │
        ▼
找「能关键词匹配到这条资讯」的已有 FocusTopic
        │
        ▼
updated_weight = clamp(0.85 × old + 0.35 × signal, -2, 2)
        │
        ▼
personalized_score = 0.7 × Σ主题权重 + 0.3 × 新鲜度
```

**五个真实瓶颈**（不是理论风险，是现在就能观察到的）：

1. **冷启动死锁**。反馈只能**修改已有主题**，不能创建主题。用户不先去 `/topics` 手建关注主题，点再多反馈都毫无效果。
2. **匹配太粗**。`text_matches()` 是正则分词 + 子串包含。搜"收购"这类泛词会命中一堆无关主题，权重被噪声带偏。
3. **无归纳能力**。系统永远不会得出结论"你最近在反复关注己内酰胺和它的下游"，只会被动等用户自己建主题。
4. **无衰减、无淘汰**。权重只增不减（除非用户点不感兴趣），一个三年前的热点主题会永远留在画像里。
5. **跨用户为零**。每个用户的偏好是孤岛。公司里 5 个做同一产品线的人，各自重复踩一遍冷启动。

> **进度（2026-10-15）**：瓶颈 1（冷启动死锁）与瓶颈 2（匹配太粗）已随 **L1.5** 修掉（附录 E）；
> 瓶颈 3（无归纳）与 4（无衰减淘汰）已随 **L2a 归纳引擎**修掉（附录 F）——
> 「老主题自然退场」没有走数值衰减，而是走**模型提出 drop 建议 + 用户确认**，
> 理由更可解释、且不会静默改变排序。瓶颈 5（跨用户为零）仍未动。

## 2.2 目标：三层学习结构

```text
L1 显式反馈快回路   ← 现在就有，保留
   点一下就更新权重，秒级生效，规则透明

L2 LLM 归纳慢回路   ← LMA 核心，新增
   攒批 → 大模型读反馈样本 → 提出「主题增/删/改」建议
   → 置信度过滤 → 高置信自动落地 / 低置信进待确认箱
   → 全程写审计，可一键回滚

L3 画像召回         ← 接已有基建
   把最终画像写进记忆库（与 long_term_memories 同套路）
   DeepResearch 研究前召回，让"研究什么"也带个人偏好
```

**L2 是关键增量**：L1 是"调参"，L2 才是"学会"。两者不冲突，L1 提供高频数据，L2 负责提炼。

## 2.3 L2 的具体机制

### 触发

- **攒批触发**：累计 N 条新反馈（建议 N=20）或距上次归纳 ≥7 天；
- **手动触发**：`/topics` 页加一个「重新归纳我的关注」按钮，给用户掌控感。

### 输入（每次归纳打包给模型）

```
近 N 条反馈记录（标题 + 摘要 + 事件类型 + 实体 + 用户的正负判断）
+ 当前生效的关注主题列表（名称/类型/权重/命中次数）
+ 用户最近的检索词
```

### 输出（结构化 JSON，不是自由文本）

```json
{
  "add_topics":   [{"name":"己内酰胺", "type":"product", "reason":"近30天正向反馈12条", "confidence":0.86}],
  "adjust_topics":[{"name":"可降解塑料", "delta":0.4, "reason":"近期反馈转向负面", "confidence":0.72}],
  "merge_topics": [{"targets":["PA6","尼龙6"], "into":"聚酰胺", "confidence":0.91}],
  "drop_topics":  [{"name":"页岩气", "reason":"180天无任何互动", "confidence":0.95}],
  "insights":     ["你近期关注集中在己内酰胺-聚酰胺产业链的产能与价格"]
}
```

### 落地的三条硬约束（人工确认模式下的安全网）

| 约束 | 做法 |
|---|---|
| **建议箱** | 模型只产出建议，**全部进「待确认」箱**，由用户逐条接受/拒绝；任何主题增删改都不由模型直接落库 |
| **可回滚** | 每次归纳产生一个 `preference_revision` 快照，一键回滚到任意历史版本；模型永远不直接改数据，只产出"建议+diff" |
| **可解释** | 每个主题变更都带 `reason` 和证据反馈 ID，`/topics` 页能点开看"为什么系统觉得你关注它" |

`confidence` 仍然输出，但**只用于给建议排序**（高置信排前面），不再作为自动生效的开关。

### 建议新增的表

```text
focus_topic_revisions   归纳快照（含 diff JSON），用于回滚
preference_suggestions  待确认建议（pending/accepted/rejected）
```
`FocusTopic` 本身复用现有表，不重构。

### 为什么不做模型微调（已确认）

用户定位是**轻量化 AI 对话 + 重点资讯搜索**，且已明确「不做模型微调」。
微调的成本（数据量、训练、部署、不可解释、不可回滚）与收益严重不匹配。
**用「LLM 归纳 + 结构化画像 + 检索加权」达到 90% 的效果，成本是微调的 1%**。
等画像数据积累到万级反馈真的不够用了，再谈微调也来得及。


## 2.4 L3：与记忆库的接入关系

现在记忆库是**只写不读**（DeepResearch 主路径没有召回）。LMA 恰好给了它一个真正的用途：

```text
L2 归纳出的画像  →  写一条 type='preference' 的记忆
                      ↓
DeepResearch 研究前召回该用户的偏好画像
                      ↓
"帮我查一下这个产品" → 自动带上"你长期关注该产业链上游"的上下文
```

也就是说：**先把 L1/L2 做出来，L3 就有了非接不可的理由**，不必现在为了接而接。

## 2.5 LMA 落地路线

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **L1.5 补漏** | 反馈能**自动创建**候选主题（打破冷启动死锁）；匹配从子串改为分词+同义词 | ✅ **已完成**（附录 E） |
| **L2a 归纳引擎** | 批量归纳 + 结构化输出 + 建议进「待确认」箱 | L1.5 | ✅ **已完成**（附录 F） |
| **L2b 建议箱 UI** | `/topics` 页展示建议、逐条接受/拒绝、可回滚 | L2a | ✅ **已完成**（附录 F，与 L2a 同批交付） |
| **L2c 跨用户共享** | 同一部门内共享/复用画像（正文 §2.1 瓶颈 5） | L2b | 未做 |
| **L3 画像召回** | 画像写入记忆库 + DeepResearch 召回 | L2b | 未做 |

**已定：不做自动落地。** 模型永远只产出「建议 + 理由 + 证据」，由人逐条确认。
因此原计划里的「置信度闸 + 自动生效」被移除，**置信度仅用于排序建议**
（高置信排前面），快照与回滚机制保留，作为误操作兜底。

# 第三部分 · 交汇点与统一信号

知识库标注和 LMA 偏好最终会走到同一处 —— **都是"人对内容/主题的判断"**，只是来源不同：

| 信号来源 | 现有载体 | 消费方 |
|---|---|---|
| 资讯反馈（感兴趣/相关） | `NewsFeedback` | LMA 画像 |
| 关注主题权重 | `FocusTopic.weight` | 资讯排序 |
| 知识库标签 | 待建 `annotations(kind=tag)` | 检索过滤 |
| 知识库重要度 | 待建 `annotations(kind=rating)` | rerank 加权 |
| 知识库评论 | 待建 `annotations(kind=comment)` | 回答引用 + LMA |

**不必现在就建"统一信号表"**（过度设计），但设计新表时保持字段命名一致（都用 `signal` / `weight` / `confidence` 语义），将来合并成本就很低。

| 2 | 标注定位 | **偏重 comment**（团队内部讨论）。K3 先只做评论 + 回复/@成员，标签/评分/划线后置 |
| 3 | 自动落地容忍度 | **保留人工确认**。模型只产出建议，不自动改数据；confidence 降级为建议排序依据 |
| 4 | 知识库是否跨组织 | 见下方判断 |

## 决策 4 的判断：**不引入 `org_id`，但补一个「可见性」档位**

用户反馈「仅限一个部门内部使用，但不确定」。我的判断依据：

- 现在只有**一个部门**，引入 `org_id` 后所有数据都是同一个值，**不产生任何判别力**，
  却要在每次查询里多带一个条件、每个新建对象上多写一个字段——纯负债。**先不做**。
- 但「部门内共用」和现有的「个人私有库 + 点对点加成员」**语义确实不同**：
  按现在模型，部门新同事入职后，必须由管理员**逐个手工添加**才能看到任何知识库，
  这在部门场景下是明显的可用性缺口。
- 因此建议补一档 `visibility`：`private`（默认，等价于现状）| `team`（部门内所有登录用户可见，
  角色默认 viewer，可被提权为 editor/manager）。
  一个字段 + 一处权限判断即可，**不需要 org_id**，也不需要动现有数据。
- 未来真要跨组织时：在 `knowledge_bases`（或 `users`）上加 `org_id`，
  把 `visibility=team` 的语义收窄为「同 org 内可见」，**现有数据无需迁移**。
  也就是说，现在不做 `org_id` 的**改造成本几乎为零**，而收益是少维护一层暂时无用的抽象。

# 附录 A · 资讯检索重复问题（本轮已实现）

用户实测：搜「BASF」时关于「收购赢创」的三条相同资讯同时进入结果。

## A.1 根因（三个叠加）

| # | 问题 | 证据 |
|---|---|---|
| 1 | 检索结果**完全不做标题去重** | 库内命中与全网命中会各占一个位置；Bocha 自身也会返回同一篇文章的多个站点版本 |
| 2 | `_persist_online` **只按 `source_url` 判重**，算了指纹却从不比对 | 同一篇文章换个 URL 就再入库一条，库内持续累积近似重复 |
| 3 | **相似度阈值不可用** | 真重复（财新稿的两个站点版本）= **0.730**；而「PA6巴斯夫…塑胶颗粒」vs「PA66…尼龙颗粒」= **0.725**、「己内酰胺…-2026年9月」vs「…-2026年8月」= **0.789**。**不存在能同时满足的单一 Jaccard 阈值** |

## A.2 方案：主力靠「主干 + 站点后缀」，Jaccard 只做保守兜底

门户转载的特征是**正文标题一字不动、只在尾部拼自己的站点名**：
`…双方确认已初步接触_新浪财经_新浪网` / `…_大风号_凤凰网` / `… _ 东方财富网`。
因此判重分三级（`titles_same_article`，展示层与入库层共用同一实现）：

1. 归一化（去空白标点、ASCII 转小写）后**完全相同**；
2. **主干相同且长度 ≥ 16**，且**至少一方尾部像站点名**
   （含「网/报/头条/财经/新闻/频道/社…」且**不含数字**）—— 抓门户转载；
3. 整体 Jaccard ≥ **0.85** —— 仅作「几乎逐字相同」的保守兜底。

「不含数字」这条是关键：否则 `-2026年9月` 会被当成站点后缀，
把同系列报告的不同月份合并掉。

配套：
- 检索侧在 **rerank 之前**去重（省 rerank 配额），库内条目优先于全网条目
  （库内条目有 id、能承载反馈、已完成抽取）；
- 沉淀侧改为**一次载入判重池、批量比对**（新增 `load_recent_pool` / `match_pool`），
  避免逐条扫描近 2000 条标题；
- 新增响应字段 `title_deduped` 与日志，便于线上观测。

## A.3 实测

| 场景 | 结果 |
|---|---|
| 搜 BASF | `title_deduped=13`；财新泄漏稿 4 条 → 1 条；收购赢创 3 条转载 → 1 条 |
| 搜己二酸（连跑两次） | 第 1 次 `persisted=9`，第 2 次 `persisted=1`（只有 1 条真正新的），沉淀防重生效 |
| 库内重复标题复查 | 未新增重复分组（仍是历史遗留的 2 组环氧丙烷日评） |
| 回归测试 | `backend/test/test_title_dedup.py`，18 项断言全过 |

## A.4 顺带修掉的更严重问题：行业相关性闸在误杀

排查去重时发现，同一批标题两次运行被剔除的数量是 **9 条 vs 12 条**（不稳定），
且被剔除的包括**「巴斯夫拟收购赢创」**和**一篇德文 BASF 报道**——都是正经化工资讯。

三处修正：
1. 提示词明确**企业的并购重组/收购/投融资属于行业经营信息**，判为相关；
2. 明确**不得因标题里的财经/医药/门户站点名**（财经网、医药新闻、大风号）判为不相关；
3. **非中文内容不做 LLM 判定，直接放行**（新增 `INDUSTRY_GATE_CJK_MIN`，默认中文占比 0.15）——
   模型读不懂的语言上，它给出的「不相关」是噪声而不是判断。

> 过程中一度加了「拿不准一律判相关」，结果闸门过松（剔除数 9 → 1，顺企网 B2B 黄页全部放回），
> 已改为**用明确的正面清单（并购=相关）替代笼统的宽松指令**，并把 B2B 代理黄页写进负面清单。

修后两次运行结果**逐条一致**，`irrelevant_filtered` 稳定为 8，
且「顺企网代理商黄页」仍被剔除、「赢创并购」与德文报道正常保留。

**已知取舍**：外文标题不做行业判定 → 会放行（如一篇俄文报道）。选择「宁可显示也不静默丢弃」，
如需过滤外文，走**独立开关**（`exclude_foreign`）而不是复用本阈值——已实现，见附录 B.3。

# 附录 C · K2 检索隔离（v0.9-kb-isolation，已实现）

## C.1 原计划 vs 实际发现

原计划只有一句"检索按 `kb_id` 可见集合过滤"。动手时发现**更严重的一层**：

# 附录 E · L1.5 反馈冷启动补漏（2026-10-10 已实现）

## E.1 原问题（正文 §2.1 瓶颈 1、2）

# 附录 F · L2a 归纳引擎 + L2b 建议箱（v0.11-lma-l2a，已实现）

对应正文 §2.5 的「**L2a 归纳引擎**」与「**L2b 建议箱 UI**」两行，同批交付。

## F.1 要解决什么（正文 §2.1 瓶颈 3、4）

| 瓶颈 | 原状 | 本次做法 |
|---|---|---|
| 3 · 无归纳能力 | 系统只会被动等用户建主题，永远得不出「你最近在反复关注 X 和它的下游」 | 模型读反馈样本，产出 `add / adjust / merge / drop / insights` 五类结构化结论 |
| 4 · 无衰减、无淘汰 | 权重只增不减，三年前的热点主题永远留在画像里 | **不走数值衰减**，改走「模型提 `drop` 建议 + 用户确认」。衰减是静默改变排序，不可解释；`drop` 是显式动作，可回滚 |
| 5 · 跨用户为零 | 仍是孤岛 | **未做**，留给 L2c |

**为什么不做自动落地**（正文 §2.3 三条硬约束的最终形态）：模型只产出「建议 + 理由 + 证据」，
全部进 `pending` 箱，由用户逐条接受/拒绝。`confidence` 只用于**排序建议**，不再作为自动生效的开关。

## F.2 数据：两张新表

```text
focus_topic_revisions   归纳快照。每次归纳先拍一张 focus_topics 全量快照（snapshot JSON），
                        另存 diff（本次产出哪些建议）、summary（画像结论）、error（失败原因）。
                        status: applied | rolled_back；每个用户只有一条 current=TRUE。
preference_suggestions  待确认建议。kind: add|adjust|merge|drop|insight；
                        status: pending|accepted|rejected；

                        reason（模型给的理由）、evidence（支撑它的反馈 id 列表）、confidence。
```

- 迁移脚本 `docker/init-db/07-lma-induction.sql`（幂等，已在运行库执行）。
- `focus_topics` 另加一列 `suggestion_id`（FK→`preference_suggestions`）——
  **回滚靠它识别「哪些主题是本次归纳新建的」**，从而做到精确回退而不是全量覆盖。

## F.3 服务：`service/lma_induction_service.py`

### 触发判定（`induction_status`）

```text
攒批：距上次归纳后新增反馈 ≥ LMA_INDUCTION_MIN_FEEDBACK（默认 20）→ due=batch
定时：距上次归纳 ≥ LMA_INDUCTION_MAX_DAYS（默认 7 天）且期间有反馈 → due=schedule
手动：/topics 页「运行 AI 归纳」按钮，force=true 直接跑
```

### 输入打包（`collect_samples` + `_prompt_blocks`）

```text
近 N 条反馈（LMA_INDUCTION_SAMPLE_LIMIT，默认 60）
  = 标题 + 摘要 + 事件类型 + 实体 + LLM 抽取主题 + 用户的正负判断 + 反馈 id
+ 当前生效的主题列表（名称/类型/权重/正负计数），最多 LMA_INDUCTION_TOPIC_LIMIT（默认 60）
```

> 注意：**用户最近的检索词本轮没有接进去**（正文 §2.3 提到过）。
> 现在检索词不落库（无 `search_history` 表），要接需先加埋点，属独立小项。

### 输出清洗（`_normalize`）——把模型输出洗成可安全落地的建议

模型难免胡说，所以每条建议都要过闸：

| 类型 | 保留条件 |
|---|---|
| `add` | 名词非空、非泛词（`is_generic`）、当前主题里不存在（含**同义已存在**：已有 `PA6` 就不会再加 `尼龙6`）、且**至少有一条样本能匹配上**（`hits > 0`，不允许凭空造主题） |
| `adjust` | 目标主题必须已存在；`delta != 0`；delta 截断在 `[-1, 1]` |
| `merge` | **按「被合并的主题记录条数 ≥ 2」判定**，不能用同义归一键数判定——`PA6 / 尼龙6 / 聚酰胺6` 在词表里本来就归一到同一 canonical，键数会退化成 1，反而丢掉最该合并的情况 |
| `drop` | 目标存在且当前启用；样本窗口无正向证据；**且历史 `positive_count == 0`**（见 F.4） |
| `insight` | 文本非空、去重后截断；每条非空结论各生成一条建议，供用户逐条确认 |

清洗复用 L1.5 的匹配算法：`_evidence_for` 内部调 `interest_scoring.text_matches`，
所以「命中判定」与资讯排序用的是同一套词表和逻辑，不会出现两套口径。

### 落地（`accept_suggestion`）

| kind | 采纳后发生什么 |
|---|---|
| `add` | 新建主题（`source='manual'`、带 `suggestion_id`）；**同名或同义已存在时只重新启用，不重复建** |
| `adjust` | `weight = clamp(weight + delta, -2, 2)`，并置为启用 |
| `merge` | 目标主题设为「规范名」，**别名并入 `query_text`**（合并后仍能命中原写法），其余成员**停用而非删除**（可回滚、不丢历史权重） |
| `drop` | 停用（`is_active=False`），不删除 |
| `insight` | 不改任何主题，只标记已读 |

`reject_suggestion` 只置 `status='rejected'`，不做任何数据改动。

### 回滚（`rollback_revision`）——精确回退，不是全量覆盖

只做两件事：

1. **删除「由本次归纳的建议创建」的主题**（靠 `topic.suggestion_id ∈ 本次归纳的建议 id` 识别）；
2. 其余主题**按快照逐字段还原**（权重/状态/计数/query_text/source）。

**归纳之后由用户手动新建或修改的主题不受影响**——这是刻意的：全量覆盖会把用户后来的手动调整一起抹掉。
同时把本次归纳遗留的 `pending` 建议置为 `rejected`（避免回滚后又冒出来），并把 `current` 交还给最近一次仍在应用中的归纳。

## F.4 两处刻意的安全护栏

**① `drop` 的第二道闸。** `_evidence_for` 只看**样本窗口内**（近 60 条）能否匹配到这个主题名。
如果一个词在窗口内恰好没被提到，`positive` 会退化成 0，于是「有正向历史的主题」会被误判为可淘汰。
所以额外要求历史 `topic.positive_count == 0` 才允许建议 `drop`：

```python
if stats["positive"] > 0:                    # 样本窗口内有正向证据
    continue
if int(topic.positive_count or 0) > 0:       # 历史上有过正向反馈 → 只允许用户手动停用
    continue
if not evidence and not (int(topic.negative_count or 0) > 0):
    continue                                 # 既无样本证据也无历史负反馈，不值得淘汰
```

**② LLM 调用收在唯一薄函数里。** `_chat_json()` 是 LMA 里**唯一**接触 AI 供应商的地方
（`base_url` / `key` / 模型名都在这里读 env），上层业务零改动。
模型不可用或输出无法解析时返回 `None`，归纳降级为「只留快照、不产出建议」，**不会抛异常打断用户操作**。

# 附录 G · 屏蔽的「弱负信号」（v0.12-weak-signal，已实现）

## G.1 问题

「资讯个人屏蔽」（v0.11 之前一批）当时**刻意留白**：屏蔽只做**过滤**，不给偏好学习任何输入。
理由是「顺手屏蔽」与「明确点不感兴趣」强度不同，混进 `news_feedback` 会稀释强负样本。

但这留下一个缺口：**用户已经把「我不想再看到这类」表达得很直接了，系统却学不到**。
本附录把屏蔽接进 LMA，作为一条**弱负信号**。

## G.2 核心设计：三通道分家

| 通道 | 载体 | 强度 | 影响 |
|---|---|---|---|
| 强正向 | `news_feedback` + `weight` ↑ + `positive_count` ↑ | 强 | 排序、L1.5 派生、L2a 归纳 |
| 强负向 | `news_feedback` + `weight` ↓ + `negative_count` ↑ | 强 | 同上（一次 ≈ -0.35） |
| **弱负向（本附录）** | `focus_topics.weak_penalty`（≤0） | **弱** | **仅个性化排序**；L2a 可作 drop 的辅助证据 |

一次屏蔽 = 对被命中的每个生效主题 `weak_penalty += WEAK_HIDE_DELTA(-0.05)`，
累计下限 `WEAK_PENALTY_FLOOR(-0.5)`（最多降半个权重，永远只是「微调」）。

排序用**有效权重** `effective_weight(topic) = weight + weak_penalty`（`feedback_learning_service`）。

## G.3 三条硬边界（写成代码注释 + 测试断言，防止被后人"优化"掉）

1. **不改 `weight`，不动 `positive_count / negative_count`** —— 弱信号与强负样本不是一回事；
2. **不写 `news_feedback`** —— 因此不会混进 L1.5 派生与 L2a 的反馈样本；
3. **可精确回滚** —— 屏蔽时把 `[{topic_id, delta}]` 写进 `news_hidden.weak_signals`，
   取消屏蔽按记录量**反向加回**。**不能**按"当前命中的主题重算"：期间用户可能改名 / 停用 / 新建主题，重算会对不上账。

## G.4 L2a 消费方式（保守优先）

- 归纳 prompt 的主题块新增「弱屏蔽N次」列，并在规则 5 明确其含义与用法；
- `drop` 建议的第三道闸放宽为：`evidence` **或** `negative_count>0` **或** `weak_hits >= LMA_WEAK_DROP_HITS(3)`；
  **前两道闸不变**——`stats["positive"]>0` 跳、`topic.positive_count>0` 跳。
  即：**有正向历史的主题，弱信号再多也不会被建议淘汰**；弱信号够多才允许"产出建议"，仍要人工确认。
- **弱字段刻意不进归纳快照 / 不参与回滚**（`_topic_snapshot` 注释）：否则回滚会把归纳之后用户新产生的屏蔽一并抹掉，属越权。

## G.5 文件与迁移

- 模型：`models/news.py`（`FocusTopic.weak_penalty/weak_hits`、`NewsHidden.weak_signals`）
- 服务：`service/news_hidden_service.py`（`apply_weak_penalty` / `_reverse_weak_penalty`）、
  `service/feedback_learning_service.py`（`effective_weight`）
- 迁移：`docker/init-db/09-news-hidden-weak-signal.sql`（`create_all` 不会给已有表补列，**必须执行**）
- 前端：`/news` 屏蔽后 toast 提示降权了哪些主题；`/topics` 权重列按"有效权重"画进度条并标注原权重，
  反馈列新增「弱屏蔽 N」标签。
