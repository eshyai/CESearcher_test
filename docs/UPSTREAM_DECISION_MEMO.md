# 上游「决定债」清单：改动成本与可行性

> **用途**：拿去和需求侧对接的输入材料。
> **基线**：commit `9384a1c` / tag `v0.11-lma-l2a`，生成于 2026-10-15。
> **共同点**：卡住下面这些议题的**不是代码，是决定**。所以每条都同时给出「代码要动多少」和「必须谁拍板」。
>
> 与「技术债」的区别：技术债可以边写边还；**决定债只会随时间变贵**——
> 用户没定 → 认证可能白做；Key 归属没定 → 配额白建；内容口径没定 → 库越大越难改；
> 供应商没定 → 将来要重建集合全量重嵌。

## 怎么读

- **成本口径**（按单人开发估）：`S` < 0.5 人日；`M` 0.5~2 人日；`L` 2~5 人日；`XL` > 5 人日或强外部依赖
- **外部输入**：不拿到就做不了、或做了会白做的信息
- **利息**：拖着的代价（决定债是涨的）

## D1 交付靶子：为谁做 / 交付成什么形态 / 什么状态算成

### 现状基线（⚠️ 修正上一轮的说法）

上一轮我说「部署从来没被当成一个任务」——**不够准确**。编排与托管代码其实**已经就绪**：

- `docker-compose.prod.yml`：backend + worker + frontend 三容器，`restart: always`，`env_file` 注入，`depends_on` 健康检查
- `backend/app/Dockerfile`、`frontend/Dockerfile`（多阶段构建 → nginx:1.27-alpine）
- `frontend/nginx.conf`：**已经处理了三件难事** —— SPA 兜底（`try_files`）、API 反代（变量 + Docker DNS 运行时解析，后端重建不 502）、SSE 关缓冲（`proxy_buffering off`，`/chat` 与 `/research` 必需）
- `compose.sh` 封装了 dev/prod 两套模式的构建与启停

**所以缺的不是开发，是决定 + 运维动作。**

### 三种交付形态与各自成本

| 形态 | 增量代码成本 | 主要工作量 |
|------|-------------|-----------|
| **A. 内网网页**（最直接） | **M~L（1.5~3 人日）** | 服务器环境/Docker、JWT 密钥（见 D5）、关自助注册、HTTPS、PG 定时备份、日志与健康检查、首次跑通 |
| **B. 企微入口**（最可能被真正用起来） | A + **M~L（2~3 人日）** | 企微自建应用、OAuth 换 userid、把 JWT 换成企微免登（或做 userid ↔ 本地账号映射）、机器人/消息卡片推送 |
| **C. 先做 Demo** | **S（0.5 人日）** | 任意内网机器起一份 prod compose，不改代码 |

### 「什么算成」——建议需求侧从下面挑 1~2 个作为验收线

1. **活跃**：部门 N 人有账号，周活跃 ≥ X 人
2. **替代**：现在某人每天花 T 分钟人工搜集资讯，工具把 T 降到 T′
3. **覆盖**：某类信息（政策发布 / 装置检修 / 竞品动态）漏报率 < X%
4. **反馈**：LMA 攒到 **≥ 200 条有效反馈**（这是 L2a 归纳真正能跑出价值的下限，见 D2）

### 可行性

**高。** 无技术未知项，全部是已知动作。主要风险在环境侧：服务器资源（Milvus + ES + PG + Redis 比较吃内存）、内网网络策略、域名与证书。

### 要拍板的点

- 首批用户是谁、多少人？（决定准入方式与是否需要角色体系）
- 形态选 A / B / C 中的哪个？
- 验收线选哪 1~2 条？

## D2 先推真实使用，还是先把 L3 画像召回做出来

### 现状基线

LMA 三层已全部打通：L1 显式反馈 → L1.5 冷启动补漏（自动派生候选主题）→ L2a 归纳引擎 + L2b 建议箱（v0.10 / v0.11）。L3 画像召回被列为「下一步」。

但整套 LMA 的价值 = **f(反馈量)**：

- `LMA_INDUCTION_MIN_FEEDBACK` = 20 条新反馈才触发攒批归纳
- 归纳样本窗口 `LMA_INDUCTION_SAMPLE_LIMIT` = 近 60 条反馈
- L1.5 自动派生主题，前提是「正向反馈里出现了词表外的新词」

**现在反馈量 ≈ 0**（唯一一次真实 LLM 归纳联调是我为验证造的样本，验证完已清理）。反馈稀疏时，归纳出来的只会是空集或噪声。

### 成本

**代码成本 = 0。这是排期决定，不是开发任务。**

如果选择「先推使用」，需要的配套是 **S~M**：把 D1 做掉 + 加一点使用引导（首页说明、反馈按钮提示）。

### 可行性

**高，且这是本文里性价比最高的一条**：不写一行代码就能拿到判断依据——*这个工具到底有人想用吗*。

### 要拍板的点

**下一轮是继续做 L3，还是先把工具推到 1~2 个真人手里跑两周，攒够 20~60 条真实反馈再回头看 L2a？**

> 参考：10-10 你对「记忆召回」做过一次同类判断，结论是「对话轻量则记忆稀疏，召回到的要么为空要么无关，反而污染 prompt」，于是选择不接。那条判断是对的，且同样适用于 LMA 的投入顺序。

## D3 成本闸与配额

### 现状基线

**零基础设施。** 全仓核实结论：

- **无** usage / quota / rate-limit 的表、中间件或统计代码
- 唯一的「配额感知」是 `bidding_service.py:305` 识别上游返回的 `quota exhausted`（被动、事后）
- `news_live_search_service` 里的「限流」是**并发控制**，不是配额
- `chat_messages.token_count`、`memories.token_count` 是单条记录字段，**没有聚合账本**

### 需要埋点的外部调用点（12 处，已逐一核实）

| 调用点 | 供应商 / 计量方式 |
|--------|------------------|
| `news_live_search_service.py:102` | 博查 Web Search，**按次** |
| `news_search_service.py:461` | `dashscope.TextReRank`（gte-rerank-v2），**按次** |
| `news_extraction_service.py:78` | qwen-turbo，**按 token** |
| `industry_relevance_service.py:128` | qwen-turbo（行业闸），**按 token** |
| `lma_induction_service.py:145` | qwen-plus（`_chat_json`），**按 token** |
| `memory_service.py:37` | qwen-plus（总结），**按 token** |
| `memory_service` + `embedding_service.py:45` | text-embedding，**按 token** |

### 分三层落地

| 层 | 内容 | 成本 |
|----|------|------|
| **第 1 层** | nginx `limit_req` 按 IP 限速 + `_persist_online` 加「每用户每日沉淀上限 / 库总量上限」+ 超限告警 | S（0.5 人日） |
| **第 2 层** | 新增 `api_usage_log` 表 + 统一埋点（建议在调用点外包一层 `call_external()` 包装器）+ 按 user / provider 聚合 | M（1~2 人日） |
| **第 3 层** | 用量看板（`/database` 旁一页）+ 超限降级（自动关全网检索 / 关 rerank） | M（1 人日） |

### 可行性

**高，无外部技术依赖。** 工作量碎但不难——难点在「12 个调用点逐个埋点后要做回归」，以及确认每个模型按什么口径计价。

### 要拍板的点

- 预算是走公司统一额度，还是按量采买？**月上限多少？**
- 超限后的降级策略由谁定（先关全网？先关 rerank？还是先关对话？）

### 利息

- 多用户上线后**按天烧钱且不可见**
- 「过阈值自动沉淀入库 + 建索引」单用户时是「按需采集」的优点，**多用户时会变成缺点**：N 个人搜同一批词，互相往同一个库灌结果 → 存储与索引成本非线性增长

## D4 内容口径与数据留存

### 现状基线

规则很齐全，但**没有成文口径**，全是补丁驱动：

- `source_quality_service.py`：四级判定（`PREFERRED_DOMAINS` 权威源白名单优先 → URL/标题强特征 → `BLOCKED_TITLE_PATTERNS` 拒绝）
- `industry_relevance_service.py`：行业相关性闸（强信号词表 + qwen-turbo 批量判定，两级）
- `_looks_foreign()`：外文过滤（按标题中文占比）

**默认行为**：过阈值的全网结果**自动入库 + 立即建索引**（`_persist_online`）。

### 要动什么

1. 一页《入库内容口径》——**谁定：法务 / 部门主管**（半天，纯文档）
2. 把口径落成配置：`NEWS_AUTO_PERSIST` 沉淀开关已有，可加「仅白名单来源自动沉淀」（S）
3. 若「付费资讯站只留元数据不留正文」→ `_persist_online` 按来源截断 / 只存标题+链接+摘要（M）

### 成本

**S~M（1~2 人日）。主要成本在拍板，不在代码。**

### 要拍板的点

- 搜到的付费资讯站内容（我的钢铁网、生意社等）**能不能留全文？**
- 保留多久？谁负责响应删除请求？
- 这个口径由法务出还是部门主管出？

### 利息

**库越大越难改。** 现在百条级，改口径只需清一批；跑一年后要回溯清理几万条，还要重建索引。

## D6 AI 供应商可替换性（三个问题的具体代价）

### 现状基线（比上一轮更具体）

**协议层：主体已统一** —— `OpenAI(base_url=...)` + `chat.completions.create`。

**隐患在配置层：**

| 问题 | 具体位置 |
|------|---------|
| **两套 base_url 变量名** | `chat_service.py:34` 用 `OPENAI_BASE_URL`；其余 8+ 处用 `DASHSCOPE_BASE_URL` |
| **模型名硬编码散落** | `qwen-turbo`（`news_extraction_service.py:82`、`industry_relevance_service.py:57`）、`qwen-plus`（`lma_induction_service.py:84`、`memory_service.py:39`）、`qwen-max`+`qwen-plus`（`deep_research_v2/agents`）、`text-embedding-v4`（`news_index_service.py:37`）、`gte-rerank-v2,qwen3-rerank`（`news_search_service.py:42`） |
| **embedding 维度硬编码** | `milvus_service.py:20` `self.vector_dim = 1024`；`embedding_service.py` 默认 `dimensions=1024` |

**三处旁路，不走 OpenAI 兼容协议：**

1. `news_search_service.py:461` —— `dashscope.TextReRank.call()`（**DashScope 原生 SDK**）
2. `chat_service.py:157` / `embedding_service.py:161` —— llama-index `DashScopeRerank`
3. DocMind 原生 SDK（AccessKey 已失效）

### 分两步，别混在一起

**阶段一：现在就能做，与公司答复无关。**
把 base_url / key / 模型名收敛到单一 `ai_provider` 配置入口，所有调用点改读它。**不改变任何行为**，纯重构。
成本 **M（1~2 人日）**：12 个调用点 + 回归测试。

**阶段二：必须等答复。**

- 若公司**不提供 rerank** → 自研（cross-encoder）或换供应商，M~L
- 若 embedding **维度 ≠ 1024** → **必须重建 4 类 Milvus 集合 + 全量重嵌**：
  `news_{industry}`、`kb_{uuid}` / `kb_{名称}`、`knowledge_base`、`long_term_memories`

### 利息的具体形态（这是最关键的一点）

| 时点 | 现在重建 | 采集跑一年后重建 |
|------|---------|----------------|
| 库规模 | 百条级 | 几万条 |
| 重建成本 | **约 0.5 人日** | **2~5 人日 + 停机** |
| 重嵌 token 成本 | 可忽略 | 可观测 |

**所以 D6 不是「等公司回复就行」的挂起项，是利息很明确的决定债。**

### 要拍板的点（三位一体，一次问清）

1. 公司提供的接口**是否 OpenAI 兼容**？
2. **embedding 维度**是多少？
3. 公司**是否提供 rerank**？
